# Security policy

## What this software does on your machine

- The LibreOffice extension runs an HTTP listener on `127.0.0.1:8660` inside LibreOffice, from LibreOffice's first window until LibreOffice quits. It accepts requests only with the pairing token and rejects unexpected `Origin` and `Host` headers. With the default settings this is the only listener.
- The pairing token is stored in the LibreOffice profile at `user/hermes-bridge/token` (mode `0600`, directory `0700`; on Windows an owner-only protected DACL) and, once you paste it, in Hermes's secret store (`LIBREOFFICE_LIVE_BRIDGE_TOKEN` in the profile's `.env`).
- With a valid token a caller can read and edit the LibreOffice documents you have open, and list the titles and file locations of all of them. Anything that can read the token file as your user can do the same.
- The extension and the plugin run no shell commands, make no third-party network calls, and have no telemetry or self-updater. LibreOffice itself can reach the network when it evaluates document content (external links, web functions in formulas); that is outside this software's control.
- The extension carries three development-only bridge operations (`dev_chat_panel`, `dev_select_text`, `dev_set_current_slide`). They refuse to run unless LibreOffice was started with `HERMES_LO_DEV=1`.

## The chat endpoint inside Hermes (off by default)

- The sidebar chat endpoint is off by default: the plugin starts it only when its setting `chat_port` is set (8661 is the port the panel calls). When it is on and the Hermes gateway runs with this plugin (`plugins.isolation: in_process`, the default), the plugin listens on `127.0.0.1:<chat_port>` for the LibreOffice sidebar panel, from when the gateway loads the plugin until the plugin is unloaded (disable, reload) or Hermes exits. It accepts a request only with the pairing token, with `Host` exactly `127.0.0.1:<port>` and with no `Origin` header, so a web page cannot use it. Bodies are bounded and strictly shaped.
- It forwards the message to the Hermes API server on loopback through the Runs API, with `API_SERVER_KEY`, which it reads through Hermes's secret lookup and keeps in memory. The key is never sent to the panel, written or logged. Its log lines carry a fixed route label, status and time only.
- A chat opened this way is your full Hermes agent (model, memory, persona) with its tools fenced: a `pre_tool_call` hook refuses every tool except this plugin's 55 document tools and the read-only `skill_view`, `skills_list`, `tool_search` and `tool_describe`. Without that fence, anything able to read the pairing token could have asked Hermes to run commands.
- What the token does allow: anything that can read the token file as your user can chat with your Hermes model (using your model credits), get replies informed by what the agent knows, and read or edit your open LibreOffice documents through it.
- The document's title is included in the message as context. It is cleaned to one printable line and labelled as a file name, but a model can still be influenced by text it reads in a document or its name; the fence limits what such text could make it do.
- The fence recognises a panel chat by the panel's session id in any of the identities Hermes gives the hook: the `session_id`, the compression-stable `conversation_id` (Hermes 0.23.1 and later), and the turn's session context.
- **Run ownership.** A run the endpoint asked Hermes for stays tracked (its chat stays busy and it counts against the limit of 4 chats) until the endpoint sees it settle. Run creation carries an `Idempotency-Key`: when the answer to a creation request is lost, the endpoint resends the same keyed request, which Hermes answers with the run it already admitted, and it never resends without the key. When a status poll fails after admission (timeout, error status, unreadable answer, refused key), the endpoint asks Hermes to stop the run with the key it was started with and watches it for up to 10 seconds. A run it cannot confirm stopped stays tracked as unresolved, and the panel is told that the outcome is not known and not to resend edits blindly.
- **Unload.** When the plugin is unloaded, the endpoint refuses new requests and asks every run whose ID it knows to stop, with the key the run was started with, also a run whose chat is still waiting on a status poll; only then does it shut its listener down (since 0.4.1; that wait is bounded by the same budget and does not happen on an event-loop thread). It watches them settle while the fence is still registered, within one 10-second budget for the plugin's own waiting: each run gets its own thread, each call only the time left, and the endpoint tries to interrupt status polls that were already waiting when unload began, when its close returns (on an event-loop thread, when the budget ends); a poll that is already reading a response body may stay blocked until that read completes or times out. The stop request does not depend on that poll. It then forgets its cached secrets. Runs it could not confirm stopped are counted and logged as unresolved, not as drained. A run whose ID arrives only after the budget (a late creation answer) is asked to stop once, best effort, and stays tracked; that stop is not made under the fence. A status answer whose `status` is not one of the states Hermes reports (any other value or JSON type) counts as a lost observation, and a stop answer without a known state is not taken as acknowledged, so the stop is asked again.

## Known limits

- **Plain HTTP bearer secrets on loopback.** Both listeners authenticate the client only. The plugin sends the pairing token to whatever listens on port 8660, the panel sends it to whatever listens on 8661 (also while the sidebar chat is off: when the panel opens and when you send a message), and the chat endpoint sends `API_SERVER_KEY` to whatever listens on the API server's port. A local process (for example another account on a shared computer) that takes one of those ports while the real listener is down could receive that secret. The file protections above do not cover this. On Windows both listeners bind 127.0.0.1 on their port with `SO_EXCLUSIVEADDRUSE` (since 0.4.1), so while they listen a second socket cannot bind that same address and port; with `SO_REUSEADDR`, which 0.4.0 used, it could. Both were seen on Windows 11 with a second socket of the same account; another account was not tried for 0.4.1. A bind of the same port number on the wildcard address (`0.0.0.0`) still succeeds; in that check such a socket did not receive a connection made to 127.0.0.1. On macOS and Linux a second bind to a port in use fails anyway. Taking a port while its listener is down is still possible on every system.
- **External-agent runtimes are unsupported for restricted sidebar chat.** Keep `chat_port: 0` when using one. An external agent such as `codex_app_server` runs its own tool loop: its built-in shell and file tools never reach Hermes's `pre_tool_call` hook, and the Hermes tools it calls arrive without the session identities the fence needs, so panel chats in such a profile would not be restricted. The dedicated-profile recipe restricts Hermes tools only; it does not disable an external runtime's built-in tools. Use a Hermes-managed model/tool loop for that recipe, explicitly configure it in the dedicated profile, disable MCP and other toolsets there, and verify the resulting configuration before enabling sidebar forwarding. The plugin does not detect the runtime itself: Hermes resolves it per turn (model settings, routes, fallbacks, provider plugins), and no published plugin API reports it.
- **Tool dispatch without an identity.** A Hermes path that calls the hook with none of the three identities is unfenced. Known cases: inner calls of `execute_code` (unreachable, because the fence blocks `execute_code`) and one helper path that does not pass `conversation_id` and is not used for API-server runs in Hermes 0.23.1.
- **Older API execution mode after compaction.** In Hermes's older, non-default API execution mode (without the canonical session owner), a compaction rotates the session id and only `conversation_id` still names the panel; a path there without `conversation_id` would be unfenced.
- **Unresolved runs at unload (accepted limitation).** When the plugin is disabled or reloaded, Hermes removes its tool restriction (the `pre_tool_call` hook) as soon as the unload callback returns, whatever the callback reports; a plugin cannot keep its hook registered beyond that. A sidebar chat that was not confirmed stopped by then keeps running without the restriction, with the user's full Hermes tools. This is an accepted, disclosed limitation of 0.4.0; it applies only after the user turns the sidebar chat on, and fixing it needs a Hermes-side per-run tool restriction. The callback returns as soon as nothing is left to wait for, which can be before its 10-second budget expires: a run whose creation was never answered has no ID, so it cannot be asked to stop and nothing waits for it. Runs can stay unresolved after a refused or unanswered stop, a revoked key, a creation whose answer never arrived, or a current tool that is still busy; a warning with the count is logged. If Hermes unloads the plugin on its event-loop thread, the plugin cannot wait there (that would block the API server answering the stops): the stops continue in the background within the same budget and the fence is removed at once; the documented unload path (`reload-plugins`) does not do this. The budget bounds the plugin's own waiting; a single API call can run somewhat past it, because socket timeouts bound each read rather than the whole call. A gateway shutdown or restart is not this case: Hermes 0.23.1 does not unload plugins when the gateway stops; it drains its API-server runs, interrupts those still going, and they end with the gateway process while the fence is still registered. The case is disabling or reloading plugins in a running gateway (`hermes plugins enable` and `disable` make it reload every plugin) while a sidebar chat is stuck; if one may be, wait for its answer or restart the gateway first.
- **Unresolved chats stay blocked.** A chat whose run is unresolved accepts no new message until a recheck, made each time you send to it again, sees the run settle; the endpoint then frees it. A plugin reload forgets the run, which does not show that it stopped. **New chat** starts another chat only while fewer than 4 runs are tracked; unresolved runs count against that limit.
- **Observed end to end once.** One real panel chat through a Hermes 0.23.1 gateway with a model (macOS), with an earlier build of this release's plugin (chat endpoint on by default, no run reconciliation), went through the Runs API forwarding, and the fence refused a terminal command in it. The fence's use of `conversation_id` after a compaction and of the turn's session context, the Runs API stop on unload, the `Idempotency-Key` replay and the handling of failed polls were checked against Hermes 0.23.1 source, its real plugin manager and fake Runs API servers, not with a running gateway and model.
- **Upgrading from a plugin build before 0.4.0** (`libreoffice-live`). Its chat listener, without the 0.4.0 changes, keeps serving `127.0.0.1:8661` until the gateway process restarts, even after the plugin is removed. Restart the gateway once after replacing it.
- **Isolation and multiple profiles.** Under `plugins.isolation: host` no chat endpoint starts. If the sidebar chat is turned on in several profiles of one gateway process, the first profile to bind a given chat port gets it, and another profile's unload does not close it. Turn it on in one profile only.
- **No approval prompt.** Writes are not confirmed per edit or per document; `document_id` selects the target, it is not a permission.

## Reporting a vulnerability

Please do not open a public issue. Use GitHub's private reporting on this repository: **Security → Report a vulnerability**. Include the LibreOffice version, the operating system, and the steps to reproduce. Never include a real pairing token.

Reports of the following are in scope: bypassing the token, `Origin` or `Host` checks on either listener; making a panel chat use a tool outside the fence through a path not listed above; obtaining `API_SERVER_KEY` through the chat endpoint; reaching either listener from another machine or from a web page; reading the token through the plugin or the extension; writing to a document other than the one named by `document_id`; and any path that makes the extension or plugin run a command or contact a third party.

## Supported versions

Only the latest release is supported. This is a small volunteer-maintained project and there is no guaranteed response time.
