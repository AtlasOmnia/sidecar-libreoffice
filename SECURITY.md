# Security policy

## What this software does on your machine

- The LibreOffice extension runs an HTTP listener on `127.0.0.1:8660` inside LibreOffice, from LibreOffice's first window until LibreOffice quits. It accepts requests only with the pairing token and rejects unexpected `Origin` and `Host` headers. With the default settings this is the only listener.
- The pairing token is stored in the LibreOffice profile at `user/hermes-bridge/token` (mode `0600`, directory `0700`; on Windows an owner-only protected DACL) and, once you paste it, in Hermes's secret store (`LIBREOFFICE_LIVE_BRIDGE_TOKEN` in the profile's `.env`).
- With a valid token a caller can read and edit the LibreOffice documents you have open, and list the titles and file locations of all of them. Anything that can read the token file as your user can do the same.
- **The extension starts a browser, and only for the Sidecar window.** When you click **Open Sidecar** while the sidebar chat is on, and only after the plugin accepted the launch, the extension opens the Sidecar window. On macOS with Chrome, Edge, Brave or Chromium installed (found at fixed paths in `/Applications` and `~/Applications`), it starts that browser as a separate process in app mode, with an argument list and no shell, a cleaned environment and its own profile in `~/Library/Caches/Sidecar for LibreOffice/browser/` (mode `0700`; empty at first, about 60 MB once used); it asks that browser to quit when LibreOffice quits. Otherwise (other Macs, and Windows in 0.5.0) it opens the page in your default browser as a normal tab: on macOS by running `/usr/bin/open` with the launch file's path, on Windows through the file association for `.html` files. On Linux the Sidecar window is not supported and the extension starts no browser. It never reads your own browser profile, cookies or keychain. Besides that browser the extension starts only these programs, each with an argument list and a cleaned environment: on macOS `/usr/bin/osascript`, to bring an open Sidecar window to the front, and `/usr/bin/open`, to open a normal tab in your default browser; on Windows the tab is opened through the file association for `.html` files, which starts your default browser. It runs no shell. The plugin starts no process.
- The extension and the plugin make no third-party network calls, and have no telemetry or self-updater. The Sidecar page loads nothing from the internet. LibreOffice itself can reach the network when it evaluates document content (external links, web functions in formulas), and a browser started for the Sidecar window can contact its vendor's services on its own; both are outside this software's control.
- Files the 0.5.0 extension writes besides the pairing folder: one-time launch files `launch-<32 hex>.html` (mode `0600`, created exclusively, in a `0700` folder `Sidecar for LibreOffice/launch/` in your user cache folder: `~/Library/Caches` on macOS, `%LOCALAPPDATA%` on Windows), each deleted within 30 seconds (a timer started when the file is written; best effort: a failed delete is not retried until the next sweep, and a suspended computer delays it), all of them when LibreOffice quits, and leftovers older than 60 seconds swept at LibreOffice start and quit, and on macOS the dedicated browser profile beside it. The Sidecar page stores only your palette and appearance choice in the browser's local storage.
- The extension carries three development-only bridge operations (`dev_open_sidecar`, `dev_select_text`, `dev_set_current_slide`). They refuse to run unless LibreOffice was started with `HERMES_LO_DEV=1`. `dev_open_sidecar` presses the panel's **Open Sidecar** button for tests, so it goes through the same launch as a click; no other bridge operation starts a browser.

## The chat endpoint inside Hermes (off by default)

- The sidebar chat endpoint is off by default: the plugin starts it only when its setting `chat_port` is set (8661 is the port the Sidecar panel calls). When it is on and the Hermes gateway runs with this plugin (`plugins.isolation: in_process`, the default), the plugin listens on `127.0.0.1:<chat_port>`, from when the gateway loads the plugin until the plugin is unloaded (disable, reload) or Hermes exits. It also serves the Sidecar web page (static files shipped in the plugin, checked against a hash list on every request) and a small API used only by that page. With `chat_port` at 0 there is no listener and the extension starts no browser.
- **Routes and credentials.** Every request needs exactly one `Host` header equal to `127.0.0.1:<port>`. The routes are separated by caller, and a request carrying another family's credential header is refused:
  - `/launcher/*`, for the 0.5.0 LibreOffice extension: a challenge-response channel keyed by the pairing token (below). No `Origin`, no fetch metadata.
  - `/ui/*`, the Sidecar page's static files: no credential. Only the files listed in `plugin/sidebar/SHA256SUMS` are served, and only while their bytes still match.
  - `/api/*`, for the Sidecar page: the session token in the `X-Sidecar-Session` header; `Sec-Fetch-Site: same-origin` when present, and required on a GET without `Origin`; on every POST exactly one `Origin` equal to `http://127.0.0.1:<port>`. A cross-site page cannot call it: it cannot send the custom header without a preflight, which is never granted, and a DNS-rebound name fails the `Host` check.
  - `/chat` and `/health`, kept compatible through 0.5.x for 0.4.0 extensions (the same requests and answers; the `Host` check and the refusal of the other families' headers are new) and deprecated for removal in 0.6.0: the pairing token as a bearer header and no `Origin` header, so a web page cannot use them.
  No route sets or reads a cookie, every response closes its connection, and bodies are bounded and strictly shaped. `OPTIONS`, `HEAD`, `PUT`, `DELETE` and `PATCH`, and `GET` or `POST` where a route does not take them, get a JSON 405 without CORS headers; any other method gets the Python standard library's plain 501 page, also without CORS headers, and reaches no route.
- **The launcher channel (the token is never sent to this endpoint by a 0.5.0 extension).** The extension sends a random 32-byte challenge to `/launcher/hello`; the endpoint answers with `HMAC-SHA256(token, …challenge…)` and a single-use server nonce, from which both sides derive a channel key. The extension checks that proof before it sends anything else. Every later call carries a counter and a MAC over the method, path, counter and body hash, and every answer to an accepted call carries a MAC over its status and body. A wrong MAC or counter drops the channel. A channel lives 120 seconds and allows 64 calls. Since `/launcher/hello` needs no credential, a new hello can only displace a channel that has not made a signed call yet (at most 16 such channels), so a flood of hellos cannot end a channel that has made a signed call (it can still make a click fail before its first call, which then says Hermes did not answer, try again); at most 16 used channels are kept, and only a signed call can displace one. A program on the port that does not know the token therefore learns nothing about it and cannot hand the extension a page to open. The exact format and test vectors are in `docs/web-protocol.md`.
- It forwards each message to the Hermes API server on loopback through the Runs API, with `API_SERVER_KEY`, which it reads through Hermes's secret lookup and keeps in memory. The key is never sent to LibreOffice or the browser, written or logged. The browser never sees a Hermes run id either, and of the chat session id only the first 8 of its 32 hex digits, shown as the chat label. Log lines carry a fixed route label, status and time only: no paths, ids, titles, messages, tokens, codes or keys.
- A chat opened this way is your full Hermes agent (model, memory, persona) with its tools fenced: a `pre_tool_call` hook refuses every tool except this plugin's 55 document tools and the read-only `skill_view`, `skills_list`, `tool_search` and `tool_describe`. Without that fence, anything able to read the pairing token could have asked Hermes to run commands.
- What the token does allow: anything that can read the token file as your user can chat with your Hermes model (using your model credits), get replies informed by what the agent knows, and read or edit your open LibreOffice documents through it.
- The document's title is included in the message as context. It is cleaned to one printable line and labelled as a file name, but a model can still be influenced by text it reads in a document or its name; the fence limits what such text could make it do.
- The fence recognises a panel chat by the panel's session id in any of the identities Hermes gives the hook: the `session_id`, the compression-stable `conversation_id` (Hermes 0.23.1 and later), and the turn's session context. In 0.5.0 the plugin mints those session ids itself; the browser never supplies one.
- **Run ownership.** A run the endpoint asked Hermes for stays tracked (its chat stays busy and it counts against the limit of 4 chats) until the endpoint sees it settle. Run creation carries an `Idempotency-Key`: when the answer to a creation request is lost, the endpoint resends the same keyed request, which Hermes answers with the run it already admitted, and it never resends without the key. When a status poll fails after admission (timeout, error status, unreadable answer, refused key), the endpoint asks Hermes to stop the run with the key it was started with and watches it for up to 10 seconds. A run it cannot confirm stopped stays tracked as unresolved, and the window is told that the outcome is not known and not to resend edits blindly. One worker thread drives each run from creation to settlement. **Stop** in the Sidecar window sends the stop to Hermes at once, with the key the run was started with, from a short-lived thread of its own, so a status poll in flight does not delay it. That thread is registered before it starts, its whole request (connect, send and answer) ends within 10 seconds or the unload budget, whichever comes first, and unloading cuts it off: from then on nothing more is connected or sent on it. Unloading then waits for these threads at most 0.25 seconds past its budget, for all of them together. A thread that has not started yet, or is still inside an operating-system connect, cannot be interrupted and can outlive unload; when it goes on it sends nothing. When Hermes unloads the plugin on its event loop, unloading returns at once and does not wait for these threads: they are cut off at the end of the 10-second budget, so until then a stop that has not connected yet can still be sent after unload returned. Before Hermes has named the run, the worker sends the stop as soon as the run is known. Only an observed settled state releases a run, once: the worker driving it reports *Stopped* once it sees the run settle, or an unknown outcome if it cannot; when no worker drives an unresolved run any more, a settled answer to its stop releases it through the same check.
- **Unload.** When the plugin is unloaded, the endpoint closes its listener, ends every Sidecar session and launch code, answers waiting page requests once that the plugin was turned off, and asks every run whose ID it knows to stop, with the key the run was started with, also a run whose chat is still waiting on a status poll. It watches them settle while the fence is still registered, within one 10-second budget for the plugin's own waiting: each run gets its own thread, each call only the time left (one deadline for the whole call, so an answer trickled byte by byte does not extend it), and the status polls and Stop requests still in flight are cut off when its close returns (on an event-loop thread, when the budget ends), also while they read an answer. Its close returns within the budget plus at most 0.25 seconds for cut-off Stop threads to end; a request whose operating-system connect is still in progress cannot be interrupted and its thread can outlive unload, but it sends nothing once the connect returns. The stop request does not depend on that poll. It then forgets its cached secrets. Runs it could not confirm stopped are counted and logged as unresolved, not as drained. A run whose ID arrives only after the budget (a late creation answer) is asked to stop once, best effort, and stays tracked; that stop is not made under the fence. A status answer whose `status` is not one of the states Hermes reports (any other value or JSON type) counts as a lost observation, and a stop answer without a known state is not taken as acknowledged, so the stop is asked again.

## The Sidecar window (0.5.0)

- **Launch code.** `/launcher/launch` mints a one-time code: 32 random bytes, stored only as a SHA-256 digest, valid for 30 seconds and one use, bound to one document, at most 16 outstanding. The code reaches the browser through the launch file above, which redirects to `http://127.0.0.1:<port>/ui/index.html#launch=<code>`, so it never appears on a process command line on any platform. The page's first script reads the code, removes it from the address and exchanges it for a session.
- **Double use.** If a code is presented a second time within its 30 seconds, the session made with it is closed, its reply is stopped, a warning is logged, and the extension's panel says another program used the launch. After that a replay is simply refused as expired, so reopening a spent link from browser history never disconnects a live window.
- **Session.** The session token is 32 random bytes, stored by the plugin only as a digest, and kept by the page only in script memory: no cookie, `localStorage`, `sessionStorage`, URL or window name. A reload or a duplicated tab has no token and shows the reconnect text. A session ends when the window closes or reloads, when a newer window opens for the same document, when LibreOffice closes the document or quits, when the plugin unloads, after 12 hours without a request, on double use, or when it is evicted (at most 8 sessions; the least recently used session without a running reply goes first). Ending a session stops its reply. While a reply runs, 90 seconds in which its window has no request following that reply (`/api/turn`) open or arriving also stops it.
- **What a session can do.** One fenced chat for one document: send, follow the reply, stop, start a new chat, close. It cannot answer approvals, steer a run, reach any other Runs API call, or see `API_SERVER_KEY`, the pairing token or a Hermes run id. A run waiting for an approval still ends at the existing 600-second deadline; the window tells you to press **Stop**.
- **Rendering.** Replies are Markdown rendered by the bundled marked, then sanitized by the bundled DOMPurify with a strict allow-list (paragraphs, emphasis, code, quotes, lists, headings, tables, rules and links; the attributes `href`, `align` and `start`; `http`, `https` and `mailto` addresses only). Every link becomes a control that shows its address with a **Copy link** button: nothing in the page navigates or opens a window. No images. Status and activity text is set as plain text. Trusted Types make any other HTML sink throw in Chromium browsers.
- **Response headers.** The page's files are served with a content security policy that allows only the page's own origin (`default-src 'none'`, no inline script or style, `connect-src 'self'`, `form-action 'none'`, `frame-ancestors 'none'`, Trusted Types), plus `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer`, `nosniff` and a `Permissions-Policy` that turns off device features. Static files other than `index.html` are refused to cross-site requests.
- **Supply chain.** The page's files are part of the plugin at its pinned commit and are never fetched at runtime; there is no service worker. marked 15.0.12 and DOMPurify 3.4.12 are vendored unminified, with their licences; `plugin/sidebar/vendor/VENDOR.json` records the npm registry tarball, its integrity hash and the file's hash, and `scripts/verify_vendor.py` re-derives them from the registry (a developer and CI tool, never run by the plugin).

## Known limits

- **Plain HTTP bearer secrets on loopback.** Both listeners authenticate the client only. The plugin sends the pairing token to whatever listens on port 8660, and the chat endpoint sends `API_SERVER_KEY` to whatever listens on the API server's port. A 0.5.0 extension never sends the pairing token to the chat endpoint (see the launcher channel above), but a 0.4.0 extension still sends it to whatever listens on 8661 (also while the sidebar chat is off: when its panel opens and when you send a message), through the legacy routes. A local process (for example another account on a shared computer) that takes one of those ports while the real listener is down could receive that secret. The file protections above do not cover this. On Windows both listeners bind their ports with `SO_EXCLUSIVEADDRUSE`, so while they listen no other program, of this or another account, can bind 127.0.0.1 on that port (a program can still bind the same port number on other addresses; Microsoft documents that such a socket does not get what is sent to 127.0.0.1, which was not checked here); on macOS and Linux a second bind to a port in use fails anyway. This was checked on Windows 11 for the extension's listener: with `SO_REUSEADDR`, which 0.4.0 and earlier 0.5.0 builds used, a socket of another account (`LOCAL SERVICE`) could bind its port while it listened, and with `SO_EXCLUSIVEADDRUSE` it could not. The listener ran in an administrator session in that check, not with LibreOffice's normal rights, and whether the second socket would have received connections was not tested. Taking a port while its listener is down is still possible on every system.
- **A port taken while a Sidecar window is open.** If the gateway stops while a Sidecar window is open and another local program then takes the chat port, the window's later requests, including messages you send, go to that program, and a reload would show that program's page. It does not learn the pairing token or the API key this way. Close Sidecar windows when you stop the gateway.
- **Normal browser tabs** (Windows in 0.5.0, and Macs without Chrome, Edge, Brave or Chromium). The page runs in your own browser profile: browser extensions can read the page (any extension allowed to read web pages), including your messages, replies and the session token, and can act in the page while it is open. The browser's history keeps the one-time launch link; it is spent once the window has connected and expires after 30 seconds. Any other program running as you can also read that history.
- **The dedicated browser profile** (macOS app window) runs without extensions and without background updates of its own components. Its history can keep the spent launch link. Browser policies set by an organization still apply to it: a forced sign-in, a blocked `127.0.0.1` or `file://` address or a proxy without a loopback exception can keep the window from connecting, and whether administrator-forced extensions load despite `--disable-extensions` has not been checked. The page never navigates away from itself, but the browser's own menus can still open other pages in that instance, which then run without component updates.
- **Window lifetime.** If LibreOffice crashes, the Sidecar window stays open; chat may still answer, but the document tools fail. A hidden or minimized window can notice that LibreOffice closed its document up to about a minute late. When a window disappears without telling the plugin (the browser was killed, for example), the panel can say *Sidecar is already open* for up to 90 seconds although no window is open. On macOS the dedicated browser's Dock icon can stay until LibreOffice quits. Closing or reloading the window stops the reply; what Hermes changed before the stop stays in the document.
- **Memory.** Each Sidecar window is a browser window. On macOS the dedicated Chrome 158 instance with one Sidecar window used about 310 MB (memory footprint of its six processes, measured once with this release); in a normal tab the cost is one more tab of your browser.
- **Another process running as you** can read the pairing token and drive both listeners, as in 0.4.0. This is out of scope.
- **External-agent runtimes are unsupported for restricted sidebar chat.** Keep `chat_port: 0` when using one. An external agent such as `codex_app_server` runs its own tool loop: its built-in shell and file tools never reach Hermes's `pre_tool_call` hook, and the Hermes tools it calls arrive without the session identities the fence needs, so panel chats in such a profile would not be restricted. The dedicated-profile recipe restricts Hermes tools only; it does not disable an external runtime's built-in tools. Use a Hermes-managed model/tool loop for that recipe, explicitly configure it in the dedicated profile, disable MCP and other toolsets there, and verify the resulting configuration before enabling sidebar forwarding. The plugin does not detect the runtime itself: Hermes resolves it per turn (model settings, routes, fallbacks, provider plugins), and no published plugin API reports it.
- **Tool dispatch without an identity.** A Hermes path that calls the hook with none of the three identities is unfenced. Known cases: inner calls of `execute_code` (unreachable, because the fence blocks `execute_code`) and one helper path that does not pass `conversation_id` and is not used for API-server runs in Hermes 0.23.1.
- **Older API execution mode after compaction.** In Hermes's older, non-default API execution mode (without the canonical session owner), a compaction rotates the session id and only `conversation_id` still names the panel; a path there without `conversation_id` would be unfenced.
- **Unresolved runs at unload (accepted limitation).** When the plugin is disabled or reloaded, Hermes removes its tool restriction (the `pre_tool_call` hook) as soon as the unload callback returns, whatever the callback reports; a plugin cannot keep its hook registered beyond that. A sidebar chat that was not confirmed stopped by then keeps running without the restriction, with the user's full Hermes tools. This is an accepted, disclosed limitation of 0.4.0 that 0.5.0 does not change; it applies only after the user turns the sidebar chat on, and fixing it needs a Hermes-side per-run tool restriction. The callback returns as soon as nothing is left to wait for, which can be before its 10-second budget expires: a run whose creation was never answered has no ID, so it cannot be asked to stop and nothing waits for it. Runs can stay unresolved after a refused or unanswered stop, a revoked key, a creation whose answer never arrived, or a current tool that is still busy; a warning with the count is logged. If Hermes unloads the plugin on its event-loop thread, the plugin cannot wait there (that would block the API server answering the stops): the stops continue in the background within the same budget and the fence is removed at once; the documented unload path (`reload-plugins`) does not do this. The budget bounds the plugin's own waiting, plus at most 0.25 seconds for cut-off Stop threads. Status polls and Stop requests still in flight are cut off at its end, but an operating-system connect already in progress cannot be interrupted (that request sends nothing once it returns), and a run creation request already sent can still be answered after it (the late run ID above). A gateway shutdown or restart is not this case: Hermes 0.23.1 does not unload plugins when the gateway stops; it drains its API-server runs, interrupts those still going, and they end with the gateway process while the fence is still registered. The case is disabling or reloading plugins in a running gateway (`hermes plugins enable` and `disable` make it reload every plugin) while a sidebar chat is stuck; if one may be, wait for its answer or restart the gateway first.
- **Unresolved chats stay blocked.** A chat whose run is unresolved accepts no new message until a recheck, made each time you send to it again, sees the run settle; the endpoint then frees it. A plugin reload forgets the run, which does not show that it stopped. **New chat** starts another chat only while fewer than 4 runs are tracked; unresolved runs count against that limit.
- **Observed end to end.** The 0.5.0 Sidecar window has not yet run with a real gateway and model. It ran on macOS against this release's plugin chat endpoint with a fake Runs API: launch, exchange, one reply, Stop, New chat, raise, closing a document during a launch, and quit; and on Windows 11 with LibreOffice 26.8.3.1 as a Firefox tab: launch from the panel, one reply, Stop, closing a document during a launch, and quit. Those runs used builds from before this release's last fixes (see the README's *Tested versions*). For 0.4.0, one real panel chat through a Hermes 0.23.1 gateway with a model (macOS), with an earlier build of that release's plugin (chat endpoint on by default, no run reconciliation), went through the Runs API forwarding, and the fence refused a terminal command in it. The fence's use of `conversation_id` after a compaction and of the turn's session context, the Runs API stop on unload, the `Idempotency-Key` replay and the handling of failed polls were checked against Hermes 0.23.1 source, its real plugin manager and fake Runs API servers, not with a running gateway and model.
- **Upgrading from a plugin build before 0.4.0** (`libreoffice-live`). Its chat listener, without the 0.4.0 changes, keeps serving `127.0.0.1:8661` until the gateway process restarts, even after the plugin is removed. Restart the gateway once after replacing it.
- **Isolation and multiple profiles.** Under `plugins.isolation: host` no chat endpoint starts. If the sidebar chat is turned on in several profiles of one gateway process, the first profile to bind a given chat port gets it, and another profile's unload does not close it. Turn it on in one profile only.
- **No approval prompt.** Writes are not confirmed per edit or per document; `document_id` selects the target, it is not a permission.

## Reporting a vulnerability

Please do not open a public issue. Use GitHub's private reporting on this repository: **Security → Report a vulnerability**. Include the LibreOffice version, the operating system, the browser and its version if the Sidecar window is involved, and the steps to reproduce. Never include a real pairing token, launch code or session token.

Reports of the following are in scope: bypassing the token, `Origin`, `Host`, fetch-metadata or session checks on either listener; using one route family's credential on another; obtaining or reusing a launch code or session token without being the Sidecar window it was made for; making the Sidecar page run script, render controls, styles or images, navigate, or load anything remote from a reply; making a panel chat use a tool outside the fence through a path not listed above; answering an approval from the Sidecar window; obtaining `API_SERVER_KEY`, the pairing token or a Hermes run id through the chat endpoint or the page; reaching either listener from another machine or from a web page; reading the token through the plugin or the extension; writing to a document other than the one named by `document_id`; and any path that makes the extension start a program other than the browser start described above, makes the plugin start a process, or makes either contact a third party.

## Supported versions

Only the latest release is supported. This is a small volunteer-maintained project and there is no guaranteed response time.
