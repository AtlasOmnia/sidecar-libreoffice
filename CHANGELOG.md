# Changelog

All notable changes to Sidecar for LibreOffice are documented here. The format follows Keep a Changelog.

## [0.5.0] - Unreleased

The sidebar chat moves into the **Sidecar window**: the chat of Sidecar for Excel, served by the plugin on loopback and opened beside LibreOffice in a browser when you click **Open Sidecar** in the Sidecar panel. The 55 document tools, the document bridge on port 8660, the tool fence and the run-ownership guarantees of 0.4.0 are unchanged. The sidebar chat is still off by default.

Tested: on macOS 27.2.1 (Apple silicon) with LibreOffice 26.8.2.2 and Chrome 158.0.8127.36, builds of this release's `.oxt` in new disposable profiles, driven against this release's plugin chat endpoint with a fake Hermes Runs API (no gateway, no model): the panel's **Open Sidecar** opened one app window beside Calc, one formatted reply, **Stop**, **New chat**, a second click raising the same window, LibreOffice's quit closing the browser, a document closed during its launch (no window, the launch released), and a quit in under 3 seconds against a chat port that answered one byte at a time. On Windows 11 with LibreOffice 26.8.3.1, a build of the `.oxt` in a disposable profile opened Sidecar from the panel button as a Firefox 160 tab; one reply, **Stop**, a document closed during its launch and quit (the tab closed itself) ran against the real plugin with a fake Runs API. Those native runs used builds from before the last fixes (the extension then differed only in two panel texts; the plugin lacked the lost-Send, immediate-Stop and hello-flood fixes below). The released files passed the unit suite on macOS and Windows, and headless Chrome 158 checks and the request matrix (`scripts/web_smoke`) against the real plugin. Not run: a real gateway and model, Edge, Brave, Edge or Chrome as the Windows default browser, NVDA, 150% scaling, the macOS Safari tab with this release, 2× or multi-display placement, VoiceOver.

### Added
- **The Sidecar window.** **Open Sidecar** in the Sidecar panel opens the Sidecar chat for that document (**Tools → Open Sidecar chat** shows the panel): the Sidecar for Excel markup and its three Omnia stylesheets, byte-identical to the pinned upstream files; formatted replies (headings, lists, tables, code, quotes); a status line, **Stop** and **New chat**; **Settings** with **Palette** and **Appearance**, where **Auto** follows LibreOffice's light or dark appearance. One window per document; a second click brings it to the front (macOS app window) or says it is already open. Closing the document closes its window.
- **Which browser.** On macOS the extension starts Google Chrome, Microsoft Edge, Brave Browser or Chromium (the first found in `/Applications` or `~/Applications`) as an app window with its own profile in `~/Library/Caches/Sidecar for LibreOffice/browser/` (about 60 MB once used), placed beside the LibreOffice window, and asks it to quit when LibreOffice quits. Without one of them, and on Windows in 0.5.0, the page opens as a normal tab in the default browser. Linux is not supported for the window.
- **Stop.** The window's **Stop** sends the stop to Hermes at once, with the run's own key, also while a status poll is still waiting for Hermes; the run's own worker reports *Stopped. Check the document for changes made before stopping.* once Hermes confirms it, or that the outcome is not known. Closing or reloading the window, and 90 seconds in which the window does not follow a running reply, stop the reply too.
- **A lost answer to Send loses nothing and never runs twice.** Each Send carries a random `send_id`; when its answer does not arrive, the window asks again with the same id (at most twice), and the plugin answers with the turn that message started instead of starting another; a request that repeats a Send still being admitted waits for it, and an id whose turn was already replaced is refused (`already_sent`). A reply that finished before the window learned of it is shown once, from the next state poll. If the window still has no answer, it says it is not known yet whether Hermes received the message, keeps **Send** and **New chat** off, follows that message's turn when a state poll shows it, and offers **Try again** with the same id; it never says the message did not arrive. State answers older than a Send or New chat are ignored, and New chat waits for its own answer (`docs/web-protocol.md` revision 4).
- Plugin routes on the chat endpoint (`docs/web-protocol.md`): `/launcher/*` for the extension, `/ui/*` for the page's files, `/api/*` for the page.
- `plugin/sidebar/`: the page, its `SHA256SUMS`, `UPSTREAM.json` (pins of the Omnia stylesheets) and `vendor/` with marked 15.0.12 and DOMPurify 3.4.12, unminified, with their licences and `VENDOR.json` (npm registry origin and hashes). `scripts/sidebar_sums.py --check` and `scripts/verify_vendor.py` (a separate CI job) check them. `NOTICE` names both libraries.
- `docs/web-protocol.md`: the frozen protocol between the plugin, the extension and the page, with the launcher channel's test vectors.

### Changed
- The Sidecar panel in the LibreOffice sidebar is now a launcher: a status line and **Open Sidecar**. The native transcript, input box, theme toggle and connectivity line of 0.4.0 are removed; the conversation is in the Sidecar window.
- The panel's messages say what to do: *Chat is off in Hermes.*, *Hermes is not paired with LibreOffice yet.*, *Your Hermes plugin is older than this extension…* (a 0.4.0 plugin: update it), *Something other than your Hermes answered on port 8661.*, *Hermes did not answer on port 8661…*, *Sidecar is busy, try again in a moment.*, *The LibreOffice plugin was turned off in Hermes.*, *The Sidecar window did not connect…*, *Sidecar is already open…*. The README sections they name are *Sidebar chat*, *Pairing* and *Which browser*.
- Replies are formatted Markdown instead of plain text, shown once when finished (no word-by-word streaming in 0.5.0).
- The chat endpoint logs a successful state poll or static file at DEBUG, every other answer and every refusal at INFO: an idle Sidecar window polls every 3 s.
- README, plugin README, `SECURITY.md`, `plugin/after-install.md`, the catalog template, `plugin.yaml` and the extension's description: the Sidecar window, which browser, the upgrade from 0.4.0, and the new disclosures below. Version 0.5.0.

### Security
- **The 0.5.0 extension never sends the pairing token to the chat endpoint.** It opens a short channel with an HMAC-SHA256 challenge-response keyed by the token, checks the endpoint's proof before sending anything else, and MACs every later call and answer with a counter. A program on port 8661 that does not know the token learns nothing about it and cannot make Sidecar open a page. The legacy `/chat` and `/health` routes stay compatible for 0.4.0 extensions through 0.5.x (deprecated, to be removed in 0.6.0), and a 0.4.0 extension still sends the token there, with the old known limit.
- **One-time launch code, session in memory.** The page gets a one-time code (32 random bytes, 30 seconds, single use, stored hashed) through an owner-only launch file, so the code is never on a process command line on any platform, and exchanges it for a session token it keeps in script memory only. No cookies. A second use of a code within its 30 seconds closes the session made with it and stops its reply. At most 8 sessions, 12 hours idle.
- **Routes are separated by credential**: each route family refuses the other families' credential headers; `/api/*` needs the exact `Host`, the page's exact `Origin` on POST and same-origin fetch metadata; static files are served only when listed in `SHA256SUMS` with matching bytes, with a strict content security policy (no remote source, no inline script, Trusted Types), `X-Frame-Options: DENY`, COOP and CORP.
- **Launcher channels survive hello floods.** `/launcher/hello` needs no credential, so a new hello can only displace a channel that has not been used yet; a channel the launcher is working with (one that made a call signed with the pairing token) is displaced only by another launcher's first signed call, the least recently used first. At most 16 unused and 16 used channels.
- **Exclusive ports on Windows.** Both listeners, the chat endpoint and the extension's bridge on 8660, bind 127.0.0.1 on their ports with `SO_EXCLUSIVEADDRUSE` instead of `SO_REUSEADDR`, which on Windows lets a socket of another account bind the same address and port while the listener runs (since 0.4.0; seen on Windows 11 for the bridge). A bind of the same port number on other addresses (the wildcard) still succeeds; Microsoft documents that it does not receive what is sent to 127.0.0.1, which was not checked.
- **Busy is not an older plugin.** When all 16 handler slots are taken, the endpoint's prepared refusal now carries the code `endpoint_busy`, and the panel says *Sidecar is busy, try again in a moment.* instead of asking you to update the plugin; a busy answer to a status poll keeps the launch waiting.
- **Unsigned answers only choose a fixed text.** A hello refused by an unloading or failing plugin shows that plugin's own sentence (*The LibreOffice plugin was turned off in Hermes.*, *The chat endpoint failed…*), never words from the answer, which is not signed; and when hellos from another program displace a launch channel between its hello and its first call, the panel says Hermes did not answer, try again, instead of blaming something other than Hermes.
- **Closing a document or quitting cancels its launch in flight.** No browser is started after it, a launch code the plugin already issued is released (which revokes it) and its launch file is deleted; a browser that was being started at that moment is asked to quit (on a close, when no other document has a window).
- **Bounded launcher calls and quit.** Every request from the extension to the chat endpoint has one deadline for the whole call (5 s; status polls end at the 20 s outcome limit), so a program on the chat port that answers one byte at a time cannot hold LibreOffice: its quit budgets 4 s for Sidecar (2 s for its requests); stalled file operations are not covered by that budget. Each launch file is deleted 30 s after it was written by a timer started when it is written, and all of them when LibreOffice quits.
- **Strict reply rendering.** DOMPurify runs with an allow-list (no forms, buttons, styles, classes, ids or images); links become copy-only controls; nothing in the page navigates or opens a window.
- **Off still means off.** With `chat_port` 0 the extension starts no process; a browser is started only by a click on **Open Sidecar** after the plugin accepted the launch. No bridge operation starts a browser, except the development-only `dev_open_sidecar`, which presses that button and exists only when LibreOffice runs with `HERMES_LO_DEV=1`.
- **Disclosures (rule 13).** The README, plugin README, `SECURITY.md` and the catalog description now say that the chat endpoint serves a web page and its API; that the extension starts a browser (or opens the default browser) on that click, never reads your browser profiles, cookies or keychain, and otherwise starts only `/usr/bin/osascript` (to raise the window) and `/usr/bin/open` (a normal tab) on macOS, or the `.html` file association on Windows, never a shell; that the plugin starts no process; what a normal browser tab exposes (your browser extensions can read the page; the history keeps the spent one-time link); the dedicated profile's limits on managed computers; and the memory a window costs. The sentence that the extension and the plugin "run no shell commands" is replaced by these.
- **Unload keeps its budget for its own stop work.** The chat endpoint's unload asks every known run to stop before it waits for its listener, ends that listener at once (it no longer waits out the 0.5 s accept poll; waking it takes no time of its own, and on an event loop nothing blocks) and waits for it only within what is left of the same budget. Every request to the Hermes API server has one deadline for the whole call; a user Stop's request is registered before its thread starts, ends within 10 s or the unload budget, and is cut off by unload, so nothing more is sent on it, also when Hermes answers it one byte at a time. Unload then waits for all user Stop threads together at most 0.25 s past its budget, never joins one that has not started (an unload during that moment no longer fails), and logs any still inside an operating-system connect, which cannot be interrupted: they send nothing when it returns. A settled run's stuck Stop holds unload up for that 0.25 s at most, not for the budget. When Hermes unloads the plugin on its event loop, unload returns at once and does not wait for these threads; they are cut off at the end of the 10-second budget.
- A malformed launcher path (non-ASCII) is refused as 404 `not_found` before any MAC is computed, instead of a 500 with an error log line.
- **Accepted limitation, unchanged.** When the plugin is disabled or reloaded, Hermes removes its tool restriction as soon as the unload callback returns; a sidebar chat that was not confirmed stopped keeps running without the restriction, with your full Hermes tools. The Sidecar window does not change this; the fix still needs a Hermes-side per-run tool restriction. On unload the plugin now also ends every Sidecar session and answers waiting page requests once.

### Removed
- The native chat transcript, input, **Theme: Dark** / **Theme: Light** toggle and connectivity line in the sidebar panel. The theme the 0.4.0 panel saved (`sidebar-theme.json`) is read once per LibreOffice run and becomes what the window's **Auto** appearance follows; without it, **Auto** follows LibreOffice's window colour. 0.5.0 never writes that file.

### Known limits
- Windows 0.5.0 has no app window: the page opens as a normal tab in the default browser. Linux: no Sidecar window.
- On macOS the dedicated browser's Dock icon can stay until LibreOffice quits; a hidden window can close up to about a minute late; if LibreOffice crashes the window stays open.
- A reconnected window does not show earlier messages. No live text or tool rows during a reply.
- Docs: README screenshots of the sidebar in Calc, Writer and Impress (`docs/assets/screenshots/`) show the native panel of 0.4.0.

## [0.4.0] - 2026-11-19

First public release. Workflow parity with the Sidecar tools for Microsoft Excel, Word and PowerPoint (baseline `7a565c9`): 55 tools, up from 31. Each change has stale-target checks, a truthful uncertain or partial outcome and an undo contract, and was accepted natively on LibreOffice 26.8.2.2 in disposable profiles. `docs/sidecar-parity.md` maps every Sidecar tool to its LibreOffice counterpart.

Tested: on macOS (LibreOffice 26.8.2.2) and Windows 11 (LibreOffice 26.8.3.1) the 0.4.0 release candidate, still under the extension's earlier identifier, was installed into a disposable profile and exercised through the plugin handlers, with cold restarts and clean quits; on Windows an 18-check plugin-handler matrix covering 25 of the 55 tools, CSV import with one-step undo, wrong-token refusal and a headless start. Freeze panes, protection, tables, sheet activation and recalculation were accepted at the development bridge and called through the plugin handler in the model-driven runs, not in an installed-package matrix. The candidate's unit suite passed on Windows (359 tests then, 16 POSIX-only skips). 29 model-driven scenarios (one run each, through an internal harness with a frontier model configured in its disposable Hermes profile, judged by document readback) together called all 55 tools: 27 passed as recorded, C1 failed only on an over-strict oracle and passes when the same readback is judged with the corrected oracle, and C4 exposed the CSV-import undo defect fixed below; C4's model-driven re-run after the fix passed. See `docs/workflow-acceptance.md`. The release candidate differs from this release in the sidebar's "Hermes is not answering" message, which now names the plugin, in source comments, in the plugin and toolset id (then `libreoffice-live`), and in the renames, security changes and packaging listed below. This release's `.oxt` (stored, SHA-256 in the README) was installed into a new disposable macOS profile through LibreOffice's deployment API and passed the plugin-handler matrix, CSV import with one-step undo, a registration check of the renamed sidebar deck, panel and commands, and a clean quit; it builds with the same SHA-256 on Windows 11, where a command-line `unopkg add` into a disposable profile registered it. Not exercised on Windows: Hermes itself (the plugin has not been installed or loaded by Hermes there; only the LibreOffice extension and the plugin's handlers and unit suite ran), the sidebar chat connected to Hermes, opening the `.oxt` by double-click, **Restart Now** and real mouse and keyboard input. Hermes versions: tested with Hermes Agent 0.23.1 (installed: CLI, plugin manager, one gateway chat); on the v0.23.3 source, run with the 0.23.1 installation's Python environment and without a gateway or model, plugin validation passed with no warnings and the plugin-manager probe (default off, failing polls, unload) gave the same results.

### Security
- **The sidebar chat is off by default.** The plugin setting `chat_port` now defaults to `0`, so the plugin starts no chat endpoint until you set it (8661 is the port the panel calls); with the defaults only the extension's listener on 8660 runs. The panel shows **Bridge unavailable** while the chat is off.
- External-agent model runtimes (for example `codex_app_server`) are unsupported for restricted sidebar chat; keep `chat_port: 0` there. The documented dedicated-profile recipe restricts Hermes tools only, is created without `--clone` (a clone copies model, runtime, persona, memory and secrets), and requires a Hermes-managed model/tool loop configured in that profile.
- The sidebar chat's tool fence also recognises a panel chat by its compression-stable `conversation_id` and by the turn's session context, so a compaction that rotates the session id keeps the fence in Hermes's default API execution mode; the remaining identity gaps are listed in `SECURITY.md`.
- The chat endpoint is owned by the plugin's registration: it starts only after the fence is registered, and disabling or reloading the plugin closes it and asks the runs whose IDs it knows to stop (through the Runs API), also a run whose status poll is still waiting, watching them settle while the fence is still in place within one 10-second budget for its own waiting. Runs that cannot be confirmed stopped are counted and logged as unresolved. A listener without its fence refuses to forward.
- **Accepted limitation (sidebar chat turned on only).** When the plugin is disabled or reloaded, Hermes removes its tool restriction as soon as the unload callback returns; a sidebar chat that was not confirmed stopped keeps running without the restriction, with your full Hermes tools. This is accepted and disclosed for 0.4.0; the fix needs a Hermes-side per-run tool restriction. A gateway shutdown or restart does not unload plugins first: it drains and interrupts its API-server runs (`SECURITY.md`).
- A run the chat endpoint started stays tracked until it is seen to settle. Run creation carries an `Idempotency-Key`, and a lost creation answer is reconciled by resending the same keyed request, never an unkeyed one. A failed or unreadable status poll, or a revoked key, makes the endpoint ask for a stop with the run's own key; a run not confirmed stopped keeps its chat and its slot, and the panel is told that the outcome is not known and not to resend edits blindly. Unknown run states, and a `status` of any other JSON type, are no longer treated as still running, and a stop answer without a known state is not taken as acknowledged.
- Cached secrets are cleared when Hermes reports them removed and on unload; a malformed `API_SERVER_KEY` is refused without being logged; error logs carry the exception class only.
- Both listeners serve at most 16 connections at once (more are refused at once) and give each request one 5-second deadline for headers and body, so a silent or trickling local client cannot pin threads.
- The extension compares the pairing token as bytes (a non-ASCII header is a 401, not a 500), and `bridge.log` carries a fixed route label and status instead of request lines.

### Packaging
- The `.oxt` and the plugin directory carry `LICENSE` and `NOTICE`. `.gitattributes` keeps LF line endings on every platform, so a Windows clone builds the same `.oxt`.
- `scripts/build_oxt.py` stores every member uncompressed and pins the creator system (Unix) besides the fixed timestamps, permissions and order, so the `.oxt` no longer depends on the zlib a Python links (macOS zlib 1.2.12, python.org zlib 1.3.1 and zlib-ng gave three different hashes for identical files) or on the operating system. The expected SHA-256 is read from one place, the README's *Install* section (the plugin README repeats it and a test keeps the two equal); `build_oxt.py --check` and a unit test compare the build with it, and CI runs the check on macOS, Ubuntu and Windows.

### Fixed
- One undo of `calc_import_csv` left the imported cells formatted as Text (`@`): LibreOffice switches a cell to Text when `setString` writes text that would read as a number or formula (`007`, `=1+1`) and does not record that switch for undo (found by model-driven scenario C4). Each imported text cell is now set to Text explicitly first, a change LibreOffice records in the same undo step, so one undo restores content and number formats exactly; imported text cells read back as Text-formatted.
- Windows: a refused panel chat request (wrong token, bad route, oversized body) could reach the panel as "the connection to Hermes was lost" instead of the refusal. The endpoint closed the socket with unread request bytes, and Windows answered with a reset. Refusals now close gracefully: after the reply the endpoint half-closes and discards what the client still sends, bounded to one 0.5 s deadline and about 128 KiB (the last read can add up to 64 KiB; the body is never read first, so a client that declares more than it sends cannot delay the refusal). This also fixes intermittent `test_chat_bridge` failures on Windows.
- `scripts/live_client.py` (development tooling) judged token privacy by POSIX mode bits, which Windows reports as 0o666, so it refused every token there. It now uses the same `private_files` check as the sidebar.
- Closing an Impress deck after `impress_add_text_box`, `impress_find_replace` or `impress_format_text` could abort LibreOffice (SIGABRT in `~SdrObject` on pyuno's GC thread). The bridge's own undo steps held the shapes they change; LibreOffice dropped those steps at close, and the shapes were released only after the document model was gone. The steps now implement `XComponent` and release everything in `dispose()`, which LibreOffice calls when it drops them.
- `calc_get_comments` returned empty text for every comment in a workbook just opened from `.xlsx` (the text is in the file; LibreOffice builds it on demand). It now reads the comment's caption when the cell reports none; the read changes nothing (document not modified, no undo step).
- `calc_format_range` `italic` always failed (`ExecutionUncertain`), and number-format codes were misread in decimal-comma locales (`0.00` showed 1234.5 as `1.235`). Codes are now English notation converted to the document locale.
- The plugin's argument checker rejected union-typed arguments (conditional-format values, filter conditions) and crashed on number arguments without bounds; every number now has bounds and the checker cannot raise.
- Formula conditional formats are anchored at the range's top-left cell (they were evaluated from A1 of the first sheet while reporting `verified`).
- Chart names are unique across the document; sort's automatic revert uses the focused-window undo guard; `undoable` compares the undo stack rather than its top title; table styles, validation readback, protection errors and full-range `if_match` fingerprints are checked before or after writing as appropriate.

### Known limits
- Slide reorder: no identity-preserving API in LibreOffice 26.8 (blocked). Pivot tables deferred; raw OOXML insertion excluded.
- Shape fill and line colours set by `impress_add_shape` are written to `.pptx` as the theme's accent colour.
- Protection does not block the bridge's own writes. `bridge.log` is outside the owner-only file guarantee.

## [0.3.0]

Not published.

### Added
- **Chat sidebar.** A Hermes deck in the LibreOffice sidebar with a chat panel (transcript, input, Send, New chat; Enter sends, Shift+Enter adds a line) and **Tools → Open Hermes chat**. The plugin runs a loopback chat endpoint inside the Hermes gateway (`chat_port`, default 8661) that checks the pairing token and forwards to the Hermes API server; a conversation continues across messages and names the panel's document. Panel chats are fenced to this plugin's tools by a `pre_tool_call` hook. Live on LibreOffice 26.8.2.2 with a throwaway Hermes 0.23.0 gateway and a real model: read, edit, undo on a follow-up message, and a refused shell command. Messages were entered through the development hook `dev_chat_panel`, not typed by hand.
- Bridge operation `show_chat_panel` opens a document's sidebar on the Hermes deck.
- 20 tools, taking the plugin from 11 to 31. ### Fixed
- An invalid cell address sent straight to the bridge was answered as an unhandled failure (HTTP 500), which the plugin client reports as `ExecutionUncertain` for a change. It is now `Validation` with `state: not_started`. The plugin already rejected such addresses before sending.
- A paragraph-mode Writer insert no longer leaves the new text after an already-empty last paragraph (or before an already-empty first one): the bridge fills that empty paragraph in place and adds a break only when the edge paragraph holds text. Undo restores the original paragraphs, including the empty one.
- Bridge undo on a background document intermittently returned `Timeout`/`not_started` after about 8 s. Live diagnosis on macOS (LibreOffice 26.8.2.2): with LibreOffice hidden, the undo timed out in 21 of 30 loop iterations. During the stall the queued main-thread call sat unstarted while LibreOffice's main thread slept in `nextEventMatchingMask` (`sample`), and any later post released it at once. The best-supported reading of `AquaSalInstance::DoYield` is a lost event-loop wakeup between consecutive posts; the undo path posts its main-thread calls back to back. Visible windows mask it because caret and repaint timers wake the loop. While a call has not started, the bridge now re-posts a no-op wakeup every 0.2 s, within the same 8 s budget, and logs how many were needed. After the fix, 40 of 40 hidden iterations (max 0.70 s) and 30 of 30 visible ones (max 0.54 s) were clean.
- **Tools → Copy Hermes pairing token** (now **Copy Sidecar pairing token**) aborted LibreOffice. The token was copied, but looking up the message-box type as a constant (it is a UNO enum) raised an exception into LibreOffice's event loop, and soffice aborted with SIGABRT. The handler now never lets an exception escape. It parents the notice on the current document window and logs failures without the token.
- `write_formula` in `calc_execute_plan` writes to the cell; it failed live with `AttributeError: setFormula` on the one-cell range object and was reported as `ExecutionUncertain`.
- **Tools → Copy Hermes pairing token** now appears: the merge properties sit in a merge-instruction node (`S1`) and target `.uno:ToolsMenu\.uno:ExtensionManager`. The old layout put the properties directly under the extension node with a bare `.uno:ToolsMenu` merge point, and LibreOffice 26.8 silently dropped the item.
- The internal E2E harness refuses proxy runtimes, passes its credential through the child environment only, drops inherited live-session variables, redacts traces before they reach disk, bounds the chat with `--max-turns`/`--run-budget`, and fails if the credential is found in any file under the disposable home or work directory.
